# 리워드와 페이백 서버 처리

서버 연결 모드는 카드 전용 리워드와 원금을 별도 장부로 관리한다. 리워드를 송금하거나 원금으로 출금할 수 없다. `004_rewards_cashback.sql`부터 적용하며, 이전 카드 결제와 저장된 이벤트 응답은 그대로 유지한다. 실제 자금·발급사·리저브 운용 수익은 연결하지 않았다.

## 확정한 정책

| 항목 | 서버 정책 |
| --- | --- |
| 정책 버전 | `standard-v1` |
| 리워드 우선 사용 | 기본 켬. 서버에 저장하며 다음 승인부터 적용 |
| 페이백 | 리워드를 제외한 원금 결제분의 1%, 원 단위 내림 |
| 월 한도 | 회원별 10,000원. 승인 시점의 한국 시간 월에 귀속 |
| 지급 시점 | 마지막 매입 또는 잔여 승인 취소로 보류액이 0이 된 때 |
| 지급 전 확보 | 승인 시 예상 최대 페이백의 월 한도와 회사 재원을 함께 확보 |
| 환불 | 원래 승인 재원 비율대로 원금과 리워드를 반환. 페이백도 회수 |
| 회수할 리워드 부족 | 원금을 차감하지 않고 조정 대기액으로 기록. 다음 리워드 유입에서 상계 |

진행 중인 승인은 페이백이 아직 확정되지 않는다. 부분 매입 후에도 보류액이 남으면 최초 확보한 페이백 전액이 `pendingWon`에 남는다. 승인 종료 때 실제 원금 순결제분으로 지급액을 확정하고 남은 한도와 재원을 돌려놓는다.

프로그램은 마이그레이션 직후 꺼져 있다. 개발 운영자가 재원을 넣고 켜야 신규 페이백을 약속하거나 리워드를 지급할 수 있다. 꺼도 이미 지급한 리워드는 사용할 수 있고, 기존 승인에 확보한 페이백과 환불 의무는 유지된다. 테스트 재원을 자동으로 만들지 않는다. 리저브 이율, 상위 멤버십, 프로모션별 정책은 이 서버 경로에 구현하지 않았다.

## 두 장부와 회사 재원

원금은 `TEST_KRW`, 리워드는 `TEST_AQUA_REWARD` 단위를 쓴다. API 필드의 `Won`은 표시 단위이며 현금 인출권을 뜻하지 않는다. 원금 잔액 `balanceWon`, `heldBalanceWon`, `totalBalanceWon`에는 리워드를 합산하지 않는다.

| 회사 계정 | 역할 |
| --- | --- |
| `system:reward_budget` | 아직 약속하지 않은 리워드·페이백 재원 |
| `system:reward_cashback_reserved` | 진행 중인 승인의 페이백 지급을 위해 확보한 금액 |
| `system:reward_backing` | 사용자 전체의 사용 가능·승인 보류 리워드와 1:1로 대응하는 금액 |

리워드 지급은 회사 재원을 backing으로 옮기고 별도 리워드 장부에 적립한다. 리워드로 매입하면 해당 backing을 카드 정산 계정에 옮긴다. 리워드 결제를 환불하면 정산 계정에서 backing으로 되돌리고 리워드를 반환한다. 원금과 리워드의 합계가 가맹점 매입액과 일치해야 한다.

회수 대기액이 생긴 뒤 들어오는 지급·환불·승인 해제 리워드는 먼저 이를 상계한다. 상계한 단위는 사용 가능 잔액이 되지 않으며 대응 재원은 회사 예산으로 반환한다. 다른 결제에 이미 확보한 리워드를 강제로 빼지 않는다.

회사 예산 부족은 `503 REWARD_BUDGET_UNAVAILABLE`로 구분한다. 사용자의 잔액 부족으로 표시하거나 추가 충전을 유도하지 않는다. 현재 회사 계정도 테스트 원장이다. 실제 은행·발급사 자금과의 연결 및 외부 대사는 별도로 구현해야 한다.

## 부분 매입과 환불

승인액을 `A`, 승인에서 확보한 리워드를 `R`이라고 하면 누적 매입액 `C` 중 리워드는 `floor(R × C / A)`다. 누적 환불액에도 같은 승인 비율을 적용하고 이전 누적 결과와의 차이만 기록한다. 부분 처리 순서나 현재 잔액으로 재원을 다시 정하지 않는다. 곱셈은 PostgreSQL `NUMERIC`, 정수 몫은 `div()`로 구해 큰 정수의 오버플로와 나눗셈 중간 반올림을 방지한다.

승인 종료 시 원금 순결제액 `E`, 그때까지의 원금 환불액 `F0`, 지급 페이백 `B`를 고정한다. 이후 원금 환불 누계가 `F`가 되면 페이백 누적 회수액은 `floor(B × (F − F0) / E)`다. `E=0`이면 지급·회수가 0이다. 지급 전에 이미 환불한 금액은 지급 대상에서 제외한다.

예를 들어 원금 100,000원, 리워드 3,000원에서 10,000원을 승인하면 원금 7,000원과 리워드 3,000원을 확보한다. 페이백 대기는 70원이다. 총 6,000원만 매입하고 승인을 종료하면 원금 4,200원과 리워드 1,800원을 사용하고 나머지를 해제한다. 페이백은 42원이다. 이후 3,000원을 환불하면 원금 2,100원과 리워드 900원이 돌아오며 페이백 21원을 회수한다.

## API와 재시도

`GET /api/account`는 원금·카드·리워드를 같은 repeatable-read 트랜잭션에서 조회한다. `rewards`에는 사용 가능·승인 보류·조정 대기, 현재 설정 버전, 월별 페이백 확정·대기·회수·남은 한도와 최근 50개 리워드 기록이 들어간다. `confirmedWon`은 회수를 뺀 지급액이며 기존 조정 대기액 상계 전 금액이다. 기록에는 사용 가능·보류·조정 대기의 실제 증감을 따로 제공한다.

`POST /api/rewards/preference`의 본문은 `{ "useFirst": true, "expectedVersion": 0 }`이다. 세션 쿠키, `X-Aqua-Account`, `Idempotency-Key`가 필요하다. 성공 응답은 `{ "useFirst": true, "version": 1 }`이다. 오래된 버전으로 변경하면 `409 PREFERENCE_CHANGED`를 반환한다. 같은 키·같은 요청은 최초 응답을 반환하고 설정을 다시 바꾸지 않는다.

화면은 요청 전 원래 계정·키·본문을 sessionStorage에 남긴다. 응답을 받지 못하면 같은 요청으로 결과를 확인한다. 새 계정에서 이전 요청을 보내지 않는다. 성공 또는 버전 충돌 뒤에는 새 계정 조회가 끝날 때까지 스위치를 잠근다. 리워드 지급·회사 예산 변경·프로그램 활성화 HTTP API는 없다.

## 로컬 확인

먼저 [서버 실행 안내](server-development.md)에 따라 DB를 시작하고 마이그레이션을 적용한 뒤 테스트 계정을 만든다. 모든 명령은 API와 같은 `DATABASE_SCHEMA`를 사용해야 한다. 운영자 명령에는 별도 `MIGRATION_DATABASE_URL`이 필요하다.

```bash
npm run db:migrate
npm run server:rewards -- budget 1000000 guide-budget-001
npm run server:rewards -- program on guide-program-on-001
npm run server:rewards -- grant alice@example.test 3000 guide-grant-001
```

같은 키·같은 내용은 재실행해도 추가 지급하지 않는다. 키를 다른 금액·대상에 재사용하면 거절한다. 이 CLI는 `NODE_ENV=production`에서 DB 연결 전에 거절한다. 실제 운영 지급의 승인·감사 절차를 대신하지 않는다. 카드 테스트는 [기존 이벤트 CLI](card-payment-server.md)를 사용한다.

```bash
npm run server:rewards -- program off guide-program-off-001
npm run server:reconcile
```

`server:reconcile`는 일반 DB 연결로 읽기 전용 repeatable-read 검사를 수행한다. 원금 전표와 잔액, 리워드 전표·이력과 잔액, 카드별 확보액, backing, 대기 페이백 재원, 월 한도와 지급·회수 계산의 일치를 확인한다. 금액은 정확한 십진 문자열로 출력한다. 기본 최대 100개 불일치와 전체 건수를 반환하며 데이터를 수정하지 않는다.

종료 코드 `0`은 내부 장부 일치, `1`은 불일치, `2`는 검사 실패다. 결과가 잘려도 전체 건수를 남긴다. 이 명령은 외부 은행·보관사·발급사 정산 확인이나 실제 지급 능력 증명이 아니다.

## 검증과 출시 경계

```bash
npm run test:server
npm test
npm run build:connected
npm run build:server
AQUA_BASE_URL=http://127.0.0.1:3001 npm run test:rewards:browser
npm run server:reconcile
```

브라우저 검사는 컴파일한 연결 화면과 API를 실행한 상태에서 수행한다. 실제 PostgreSQL과 개발 운영자 CLI로 리워드 결제·부분 매입·환불·회수 부족·설정 응답 유실을 확인한다. 테스트가 만든 계정과 장부는 개발 DB에 남으며 실제 자금은 사용하지 않는다. 검사 개수와 통과 여부는 해당 커밋의 CI를 기준으로 한다.

2026-11-19 로컬 검증: 서버 109개, 제품·클라이언트 127개, 연결 브라우저 28개(송금 12·카드 8·리워드 8)가 통과했다. Chromium 320px 화면을 확인했고, 기존 개발 데이터와 별도 리워드 검사 스키마 모두 내부 대사 불일치가 0건이었다. 실제 모바일 기기와 외부 정산을 검사한 결과는 아니다.

운영 품질을 위해 원장 불변성, 제한된 DB 역할, 원자적 재원 이동, 요청 중복 방지, 설정 동시 변경, 업그레이드 호환성과 내부 대사를 구현했다. 전체 서비스가 출시 가능한 상태라는 뜻은 아니다. 실제 카드사 이벤트 서명·내구성 있는 수신·재처리, 승인 만료·늦은 매입·분쟁, 실제 자금과 외부 대사, 운영 알림·부하 시험·백업 복구 및 iOS·Android 실기기 검증은 남아 있다.
