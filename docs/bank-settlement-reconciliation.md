# 카드 정산과 은행 입출금 대사

운영자는 발급사가 통지한 정산 건마다 Aqua 계좌에서 얼마가 빠져나가거나 들어와야 하는지 계산하고, 은행에 기장된 내역과 대조한다. 먼저 해당 영업일의 매입·환불 전체를 Aqua 원장과 맞춘다. 이 단계가 일치해야 은행 대사로 넘어간다. 현재 예제와 계산 기준은 `TEST_KRW` 샌드박스용이다. [발급사 명세서와 원장 대사](issuer-statement-reconciliation.md)

## 입력 자료 준비

한 번에 한국 시간으로 마감한 카드 영업일 하나와 은행 정산일 하나, 정산 계좌 하나를 처리한다. 은행 정산일은 카드 영업일과 같거나 그 이후여야 한다. 통지서와 은행 자료의 정산일·통화·계좌가 같아야 한다. 입력은 각각 최대 4 MiB의 UTF-8 JSON 파일이다. 각 파일에서 카드 이벤트, 정산 건, 은행 전표는 종류별로 최대 10,000건까지 처리한다.

| 자료 | 원본에서 확인할 항목 |
| --- | --- |
| 발급사 매입·환불 명세서 | `businessDate`의 거래 전체와 원본 검산값을 준비한다. 개별 거래의 고유 참조는 `eventId`다. [명세서 예제](examples/issuer-statement.json) |
| 발급사 정산 통지서 | `businessDate`, `settlementDate`, `accountRef`를 확인한다. `batches`에 정산 참조 `batchId`, 여기에 포함된 `eventIds`, Aqua가 지급할 수수료 `feeWon`을 기록한다. 수수료가 없으면 `"0"`이다. 명세서의 각 이벤트는 한 정산 건에 한 번씩 포함돼야 한다. [정산 통지서 예제](examples/settlement-advice.json) |
| 은행 입출금 명세서 | 해당 계좌·정산일에 기장이 완료된 정산 거래 전체를 가져온다. `rows`에는 은행 고유 거래번호 `postingId`, 입출금 내역에서 확인한 정산 참조 `batchId`, Aqua 계좌 기준 방향과 금액을 기록한다. `controls`에는 건수와 출금·입금 총액을 각각 넣는다. [은행 명세서 예제](examples/bank-statement.json) |

은행 자료의 범위는 계좌, 기장일, 계약상 정산 거래 구분 등 은행에서 확인할 수 있는 기준으로 정한다. 발급사가 통지하지 않은 출금도 이 범위에 들어오면 그대로 포함한다. 정산 참조는 은행 쪽 원본 또는 확인된 대응표에서 가져온다. 금액과 날짜만 같아 참조를 추측해야 하는 건이 있으면 원본을 확보한 뒤 대사를 재개한다. 은행의 전체 건수·입출금 총액을 변환 결과와 비교하면 다운로드 도중 빠진 페이지도 점검할 수 있다.

`accountRef`에는 양쪽 원본의 같은 계좌에 부여한 대체 식별자를 사용한다. 계좌번호·카드번호·예금주·거래 메모는 입력에서 제외한다. 파일에는 `version: 1`, 통화 `TEST_KRW`를 사용하고 원 단위 금액은 십진 문자열로 적는다. 은행의 `debit`는 출금, `credit`은 입금이며 금액은 두 방향 모두 양수다.

## 정산 금액 계산

정산 건의 **매입 합계에서 환불 합계를 빼고 발급사 수수료를 더한다.** 결과가 양수면 은행 출금 한 건, 음수면 절댓값만큼 입금 한 건이 예상된다. 0원이면 그 정산 참조에 은행 전표가 없어야 한다.

예제는 2025년 11월 26일 카드 거래가 다음 날 은행에 반영된 경우다. 수수료 3원은 계산 검증을 위한 가정이다. 실제 수수료는 제휴 계약과 통지서에서 확인한다.

| 정산 참조 | 매입 | 환불 | 수수료 | 예상 은행 거래 |
| --- | ---: | ---: | ---: | --- |
| `clearing-a` | 100원 + 50원 | 0원 | 3원 | 153원 출금 |
| `clearing-b` | 0원 | 30원 | 0원 | 30원 입금 |

전체 순출금은 123원이다. 은행에 154원 출금과 31원 입금이 찍혀도 순출금은 123원이므로, 대사 결과는 정산 참조별로 비교하고 입출금 총액도 방향별로 확인한다.

## 실행 및 결과 확인

정산 전용 계정의 `SETTLEMENT_DATABASE_URL`과 대상 `DATABASE_SCHEMA`를 설정한다. 다음 명령은 복원 훈련의 마지막 결제까지 기록된 DB와 위 세 예제를 사용한다. 빈 DB에서 같은 파일로 실행하면 원장에 없는 거래가 먼저 보고된다. [전용 계정 설정](issuer-statement-reconciliation.md#실행)

```bash
npm run --silent server:reconcile:bank -- \
  docs/examples/issuer-statement.json \
  docs/examples/settlement-advice.json \
  docs/examples/bank-statement.json
```

배포 이미지에서는 `node dist-server/reconcile-bank-settlement.js`에 같은 순서로 파일 세 개의 경로를 전달한다.

| 종료값 | 결과와 후속 확인 |
| --- | --- |
| `0` | 원장·발급사 이벤트가 일치하고, 은행 입출금도 정산 건별로 일치한다. |
| `1` | `stage`가 `issuer_statement`이면 원장과 발급사 명세서의 차이를 먼저 조사한다. `bankSettlement`는 `null`이다. `stage`가 `bank_settlement`이면 해당 정산 참조의 통지서와 은행 원본을 대조한다. 누락·추가 거래, 은행 거래번호 중복, 방향·금액 차이를 확인한다. |
| `2` | 검사를 완료하지 못했다. 표준 오류의 코드에 따라 파일 형식·검산값, 마감일, 계좌·통화, 이벤트의 정산 배정, DB 연결과 권한을 확인한다. |

`bankSettlement.expectedTotals`와 `bankSettlement.bankTotals`에서 예상·실제 출금액과 입금액을 확인한다. `bankSettlement.findingCount`는 차이가 있는 정산 참조의 수다. 상세 내역은 100건까지 표시하며, 더 있으면 `findingsTruncated`가 참이다.

마감 전인 정산일에는 `SETTLEMENT_DAY_OPEN`이 반환된다. 한국 시간으로 다음 날 0시 이후에 다시 실행한다.

이 도구는 원장을 읽어 보고서를 출력한다. `accountRef`는 대사한 계좌의 별칭이다. `sourceSha256`에는 입력한 정규화 파일 세 개의 SHA-256 값이 담긴다. 원본 파일과 원본 검산값, 정규화 파일, 실행한 릴리스, 결과 보고서를 접근이 제한된 정산 기록에 함께 보관한다. 차액을 조사한 사람이 확인한 원인과 처리 근거도 기록한다.

## 실제 제휴 자료로 확인할 범위

버전 1은 영업일 하나의 이벤트 전체가 정산일 하나에 배정되고, 0원이 아닌 정산 건마다 은행 전표 한 건이 기장되는 경우를 다룬다. 여러 영업일을 모아 한 번에 이체하거나 은행이 정산 한 건을 여러 전표로 나누는 계약이면 전체 배치 구조를 먼저 확인한다. 원본의 일부만 골라내거나 분할 전표를 합쳐 입력하면 실제 누락·중복을 가릴 수 있다.

실제 적용 전에는 발급사와 은행의 샘플로 기장일·가치일, 정산 참조의 전달 경로, 전용 계좌의 거래 범위, 수수료 부호를 확인한다. 환전, 수수료 환급, 차지백, 예치금 증감, 별도 수수료 출금은 각각 계약상 기장 방식을 확인하고 지원 범위를 확장해야 한다.
