# 고객 거래 자격과 로그인 기기 관리

2026-11-19 기준 서버 연결 모드의 구현입니다. 로그인 성공과 거래 가능 상태를 분리합니다. 여기서 `active`는 테스트 거래 허용이며, 실제 본인확인·AML 심사나 금융 서비스 이용 승인 증명은 아닙니다. 실제 공급업체의 고객확인 결과 수신, 이메일 소유 확인, MFA·패스키, 금융 거래 추가 인증과 운영용 복구 발송은 후속 작업입니다.

## 고객 상태

`GET /api/account`의 `access`에는 `status`, `version`, `updatedAt`, `canTransact`를 반환합니다. 신규 가입자는 `unverified`로 시작합니다. 마이그레이션 전 가입자도 기존 인증 여부를 추정하지 않고 `unverified`로 초기화합니다.

| 상태 | 의미 | 새 송금·카드 승인·잠금 해제 |
| --- | --- | --- |
| `unverified` | 거래 전 확인 필요 | 차단 |
| `pending_review` | 검토 대기 | 차단 |
| `active` | 테스트 거래 허용 | 기존 한도·카드 상태 정책도 충족해야 허용 |
| `restricted` | 거래 제한 | 차단 |
| `frozen` | 거래 중단 | 차단 |
| `closed` | 새 거래 이용 종료 | 차단, 상태 재개 불가 |

잔액·거래 내역 조회와 카드 잠금은 제한 상태에서도 사용할 수 있습니다. 이미 승인된 결제의 매입·취소·환불은 계속 처리하고, 완료된 요청의 동일 키 재조회는 최초 결과를 반환합니다. 제한을 해제해도 과거 거절된 카드 이벤트가 새 승인으로 바뀌지 않습니다.

회원 송금은 보내는 사람과 받는 사람 모두 `active`여야 합니다. 새 카드 승인과 카드 잠금 해제에도 상태 검사를 적용합니다. 테스트 금액 지급, 회사 리워드 예산·적립, 기존 결제 정산은 신규 고객 지시 송금과 구분합니다. `closed` 변경만으로 잔액 반환·계정 탈퇴·개인정보 삭제가 완료되는 것은 아닙니다.

## 상태 변경과 원장 보호

일반 HTTP API에는 고객 상태 변경이나 셀프 승인 경로가 없습니다. `CustomerAccessStore.transition`은 별도 특권을 가진 테스트 운영 명령이며 production 환경에서 실행하지 않습니다. 상태 변경은 예상 버전, 요청 키, 사유를 요구하고 DB 로그인 주체와 함께 변경 불가 이력에 기록합니다. 같은 요청 재시도는 최초 결과를 반환하며, 다른 내용이나 주체로 키를 재사용하면 거절합니다. 동일 상태로 중복 전환하거나 `closed`를 다시 열 수 없습니다.

테스트 운영자는 `USER_ID`를 계정 UUID로 바꿔 상태를 조회합니다. 변경 명령은 별도 `MIGRATION_DATABASE_URL`이 필요합니다. 예시 버전 `1`은 상태 조회 결과와 일치할 때만 사용하고, 모호한 응답을 재확인할 때는 원래 버전·요청 키·내용을 그대로 사용합니다.

```bash
npm run server:customer:access -- status USER_ID
npm run server:customer:access -- set USER_ID active 1 test-review-001 'Approved disposable account for sandbox testing'
```

API DB 역할에는 상태 조회 함수와 거래 자격 검사 함수만 허용합니다. 고객 상태·이력 테이블 접근이나 운영 명령 실행 권한을 부여하면 시작 시 권한 검사가 거절합니다. DB 관리자는 신뢰 경계 안에 있으며 운영자 개인 식별과 승인 분리는 별도 운영 체계가 필요합니다.

상태 검사는 금융 트랜잭션 내부에서 공유 잠금을 유지합니다. 상태 변경은 같은 행을 배타적으로 잠그므로 동결과 송금·승인이 겹쳐도 커밋 순서에 맞는 결과가 납니다. 송금은 요청별 잠금과 기존 결과 확인 후 고객 상태, 금융 계정 순서로 잠급니다. 원장 삽입과 카드 이벤트에도 DB 트리거 검사를 적용합니다. 애플리케이션의 버튼 비활성화만으로 보호하지 않습니다.

카드 승인 정책 버전 2는 결정 당시 고객 상태와 버전을 보관합니다. 기존 버전 1의 승인 기록과 결과는 수정하지 않습니다. 새 운영 보고서에는 `customerAtDecision`이 추가되며, 이전 승인에는 `null`입니다. 이미 커밋된 과거 운영 보고서를 재조회하면 필드가 없는 원래 결과를 그대로 반환합니다.

## 로그인 기기와 최근 인증

로그인 기기는 브라우저가 제공하는 정보를 바탕으로 OS·브라우저 종류만 표시합니다. 신뢰할 수 있는 기기 인증이나 고유 하드웨어 식별이 아닙니다. 원본 User-Agent와 IP를 기기 표시 목적으로 저장하지 않습니다. 공개 세션 UUID는 쿠키의 비밀 토큰·저장 해시와 별개입니다.

- 세션 유효기간은 7일로 고정하며 활동으로 늘리지 않습니다.
- 최근 활동은 최대 5분 간격으로 갱신합니다.
- 계정당 최대 20개 세션을 유지하고, 새 로그인 시 오래된 세션부터 종료합니다.
- 가입·로그인 또는 올바른 비밀번호 재확인은 현재 세션에 최대 5분간 최근 인증을 부여합니다. 세션 만료를 넘기지 않습니다.
- 선택 기기 해제와 다른 모든 기기 해제는 최근 인증이 필요합니다. 본인 세션인지, 아직 유효한지, 최근 인증이 남았는지를 변경 트랜잭션 안에서 재검사합니다.
- 비밀번호 재설정은 모든 기존 세션을 종료합니다. 비밀번호 검증 중 재설정이 일어나면 옛 비밀번호로 최근 인증을 부여할 수 없습니다.

| 경로 | 동작 |
| --- | --- |
| `GET /api/auth/sessions` | 현재 계정의 세션 목록과 `reauthenticatedUntil` |
| `POST /api/auth/reauthenticate` | `{password}`로 현재 세션 비밀번호 재확인 |
| `POST /api/auth/sessions/revoke` | `{sessionId}`로 본인 세션 하나 해제 |
| `POST /api/auth/sessions/revoke-others` | 현재 세션을 제외한 본인 세션 해제 |

모든 경로는 세션 쿠키와 `X-Aqua-Account` 일치를 요구합니다. POST에는 기존 Origin 검사도 적용합니다. 비밀번호 오류는 로그인 자체를 해제하지 않습니다. 현재 세션 해제 성공 시 쿠키를 지우며, 다른 회원의 세션 ID는 사용할 수 없습니다. 네트워크 장애로 결과가 불명확하면 로그인 목록을 다시 확인합니다.

이 기능의 최근 비밀번호 확인은 MFA가 아닙니다. 금융 거래의 재인증 강제에도 아직 사용하지 않습니다. 실제 출금 구현 시 해당 금융 트랜잭션 안에서 인증 검사와 위험 정책을 연결해야 합니다.

## 배포 전환

009와 010은 적용된 과거 마이그레이션을 수정하지 않고 추가합니다. 기존 계정이 모두 거래 제한 상태로 바뀌므로 테스트 운영자도 일괄 자동 승인해서는 안 됩니다. 필요한 테스트 계정만 사유를 남겨 명시적으로 허용합니다.

010은 기존 세션에 공개 ID와 최근 활동을 추가합니다. 과거 세션의 최근 비밀번호 인증은 인정하지 않습니다. 기존 세션이 20개보다 많으면 가장 오래된 초과 세션은 종료되므로 해당 기기에서 다시 로그인해야 합니다.

1. 기존 API와 작업자를 정지하거나 요청을 비우고 DB 백업을 확보합니다.
2. 새 릴리스의 `npm run db:migrate`로 009·010을 적용하고 기존 DB 역할 권한을 다시 부여합니다.
3. 새 API와 작업자를 시작하고 역할 검사·계정 조회·제한 상태·기존 결제 정산을 확인합니다.
4. 테스트 계정의 거래 허용은 별도 운영 명령으로 처리합니다.

010 이후 옛 바이너리는 신규 세션 필수 필드를 제공하지 못합니다. 구버전과 혼합 운영하거나 이미지 교체만으로 롤백하지 않습니다. 이미 적용된 DB 이력을 되돌리는 대신 검증된 수정 배포·복구 절차를 사용해야 합니다. 실제 운영 인프라에서의 복구 훈련 완료를 의미하지 않습니다.

## 검증 범위

PostgreSQL 통합 검사에서 신규·기존 계정 기본 제한, 송금 양쪽 상태, 동결과 금융 요청 경합, 과거 요청 재조회, 환불·매입 유지, 변경 이력·권한 보호를 확인합니다. 세션 검사에서는 다른 회원 ID, 만료·해제된 호출자, 비밀번호 재확인 실패, 재설정·로그인·해제 경합, 20개 제한 및 기존 DB 업그레이드를 확인합니다.

연결 브라우저 검사와 실행 명령은 README와 서버 개발 안내를 참고합니다. 이 검증은 테스트 원장과 웹 브라우저 범위이며 실제 신원 검증, 발급사 인증, 실기기 테스트, 독립 침투시험을 대신하지 않습니다.

`npm run test:security:browser`는 컴파일된 서버와 연결 화면을 별도 PostgreSQL 스키마에서 실행합니다. 먼저 `npm run build:server`, `npm run build:connected`를 실행하고 로컬 `TEST_DATABASE_URL`과 제한된 `DATABASE_URL`을 설정합니다. 신규 제한 상태, 거래 도중 동결, 원격 세션 해제, 최근 인증 만료·비밀번호 오류, 현재 세션 종료와 320px 키보드 접근을 확인합니다.
