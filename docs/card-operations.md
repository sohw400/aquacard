# 카드 거래 운영 조회

`server:card:ops`는 이벤트 번호 또는 inbox UUID로 카드 거래를 추적한다. 승인·거절 결정, 실제 원장 이벤트, 수신함 처리 상태와 관련 결제 금액을 하나의 스냅샷으로 확인한다. 회원 화면이나 공개 HTTP API는 아니다. 이 도구로 승인 결과·잔액·카드 상태를 바꾸거나 이벤트를 재처리할 수 없다.

## 전용 권한

008 마이그레이션과 `DATABASE_OPERATIONS_ROLE` 권한 설정을 적용한다. 조회 프로세스에는 `OPERATIONS_DATABASE_URL`만 별도로 주며 API·수신·작업자·발신·마이그레이션 역할과 분리한다. 이 값이 없으면 다른 DB 주소로 대체하지 않는다. 시작할 때 마이그레이션과 제한된 역할을 검사하며 관리자 권한, 다른 역할로의 전환, 직접 테이블 접근이나 금융 함수 실행 권한이 있으면 중단한다.

새 로컬 DB는 `docker/postgres-init.sql`이 `aqua_operations` 역할을 만든다. 기존 로컬 볼륨에는 새 역할을 먼저 생성한 뒤 `npm run db:migrate`를 실행한다. 로컬 계정 예시는 `.env.example`에 있으며 운영 비밀번호로 사용하지 않는다. 실제 운영에서는 별도로 발급한 접속 정보와 검증 가능한 TLS 인증서를 사용한다. 조회 명령 자체는 운영 모드에서도 허용하지만 sandbox 거래를 실제 발급사 거래로 바꾸지는 않는다.

역할에는 준비·결과 조회 함수 실행과 마이그레이션 확인 권한만 부여한다. 승인 결정, 결제, 수신함, 발급사 명령과 조회 기록 테이블을 직접 읽거나 수정할 수 없다. 조회 준비 함수만 변경 불가 조회 기록을 추가한다.

`OPERATIONS_DATABASE_URL`은 조회 기록을 저장할 수 있는 주 DB를 가리켜야 한다. 원장을 변경하지 않는 도구지만 준비 단계에는 감사 기록의 쓰기가 필요하다. 읽기 전용 복제본에서 새 조회 기록을 만들 수는 없다.

## 사용 방법

조회 요청 번호는 소문자 UUID다. `node -e 'console.log(require("node:crypto").randomUUID())'`로 새 번호를 만들 수 있다. 아래 `REQUEST_UUID`, `EVENT_ID`, `INBOX_UUID`를 실제 테스트 식별자로 바꾼다.

```bash
npm run server:card:ops -- trace-event EVENT_ID REQUEST_UUID SUPPORT-1042
npm run server:card:ops -- trace-inbox INBOX_UUID REQUEST_UUID INCIDENT-208
npm run server:card:ops -- read REQUEST_UUID
```

서로 다른 조회에는 서로 다른 요청 번호를 사용한다. 마지막 인자는 내부 사건·문의 참조값이며 영문·숫자와 `.`, `_`, `:`, `-`만 허용한다. 이메일·전화번호·자유 형식 메모는 넣지 않는다. 참조값이 실제 티켓인지 확인하는 외부 시스템 연동은 없다.

응답이 끊기면 같은 DB 로그인으로 `read REQUEST_UUID`를 실행한다. 기록이 없다면 원래 조회 명령을 같은 요청 번호와 내용으로 다시 실행할 수 있다. 자동으로 새 요청 번호를 만들어 재시도하지 않는다. 같은 번호에 다른 조회 대상이나 사건 참조를 넣으면 충돌로 거절한다.

같은 요청의 결과는 처음 준비한 상태로 고정된다. 이후 결제가 매입되거나 잠금이 해제돼도 기존 결과가 바뀌지 않는다. 최신 상태는 새 요청 번호로 조회한다. `found: false`인 조회도 기록되므로 나중에 이벤트가 도착해도 옛 결과는 그대로다.

컴파일한 진입점은 `node dist-server/card-operations-operator.js`다. 종료 코드는 성공 0, 잘못된 요청·요청 충돌·조회 기록 없음 1, DB·권한·마이그레이션·처리 장애 2다. 조회 대상 이벤트가 없어 `found: false`를 반환한 것은 정상 조회이므로 0이다. 표준 출력에는 성공한 결과 JSON만 쓰고, 오류에는 접속 주소·SQL·원본 거래를 포함하지 않는다.

## 결과 해석

| 필드 | 의미 |
| --- | --- |
| `authorization` | 007 이후 승인 성공 또는 카드 상태에 따른 거절 결정. 당시 카드 상태와 정책 버전 포함. |
| `ledgerEvent` | 실제 반영된 승인·매입·취소·환불. 구버전 승인에는 `legacyPolicy: true` 표시. |
| `inbox` | 접수·처리·재시도·최종 실패 상태와 최근 20번의 처리 시도. 초과하면 `attemptsTruncated: true`. |
| `payment` | 해당 원장 이벤트의 회원과 결제가 일치하는 현재 결제 금액. 원장 이벤트가 없으면 연결하지 않음. |
| `issuerCommand` | 승인 결정에 연결된 발급사 명령의 조회 시점 상태. 결정 당시 상태는 `authorization.cardAtDecision`에 별도로 보존. |
| `correlation` | 관련 원본 입력이 일치하면 `consistent`, 다르면 `conflict`. 한 출처만 있으면 `single_source`, 아무 기록도 없으면 `not_found`. |

접수만 된 inbox를 승인으로 표시하지 않는다. 카드 상태 거절 이력이 없다는 사실도 승인 성공의 증거가 아니다. 잔액 부족 등 직접 금융 명령의 롤백은 별도 정책 결정 이력을 만들지 않으며, inbox로 받은 경우 처리 오류가 남는다. 금융 실패와 카드 상태 거절의 차이는 [카드 승인 정책](card-authorization-policy.md)을 따른다.

동일 이벤트 번호로 다른 회원·금액·내용이 들어왔다면 `conflict`를 확인한다. 각 출처의 식별자는 따로 유지하고, 충돌한 수신함 정보로 다른 회원의 결제를 연결하지 않는다. 원본 JSON, 가맹점·회원 이름, 연락처, 공급업체 카드 참조, 재전송 키와 임대 토큰은 결과에 포함하지 않는다.

## 조회 기록과 결과 공개

조회 준비는 `REPEATABLE READ` 또는 `SERIALIZABLE` 트랜잭션에서 수행한다. 여러 테이블을 같은 시점의 데이터로 읽고, 제한된 결과와 요청 내용·DB 로그인·시각·생성 트랜잭션 ID를 함께 저장한다. 준비 함수의 반환값은 접수 정보뿐이며 조회 결과나 대상 존재 여부는 포함하지 않는다.

CLI가 준비 트랜잭션을 커밋한 뒤 별도 트랜잭션으로 저장된 결과를 읽는다. DB 함수도 생성 트랜잭션 안에서는 결과 공개를 거절하므로 savepoint나 롤백으로 조회 기록만 지우면서 결과를 가져갈 수 없다. 다른 연결에서도 커밋 전 기록은 보이지 않는다. 기록 저장에 실패하면 결과를 공개하지 않는다.

기록의 주체는 호출자가 입력한 이름이 아닌 `session_user`, 즉 인증된 DB 로그인이다. 공용 접속 계정을 쓰면 개별 사람을 식별하지 못하므로 실제 운영 계정 배포 방식에 맞춰 해석해야 한다. 다른 DB 로그인은 같은 요청 번호의 결과를 읽을 수 없다. 기존 결과를 다시 읽을 때마다 별도의 접근 기록을 추가하는 기능은 아니며, 외부 DB 접근 로그나 보존·보관 정책을 대신하지 않는다.

## 검증 범위

실제 PostgreSQL 검사는 커밋 전 공개 차단, savepoint·롤백·다른 연결, 동시 요청, 고정 결과 재조회, 조회 대상 없음, 충돌 표시, 시도 이력 제한, 권한 오부여와 기존 승인 데이터 호환성을 확인한다. CLI 검사는 잘못된 입력을 DB 연결 전에 거절하고 오류에서 비밀값을 제거하는지 확인한다. CI는 컴파일한 명령을 일반 사용자 권한·읽기 전용 컨테이너에서 실행하고, 별도 프로세스로 같은 기록을 다시 조회한다.

2026-11-19 로컬 검증에서 신규 검사 31개를 포함해 서버 검사 234개와 클라이언트 검사 139개가 통과했다. 컴파일한 CLI의 준비·재조회와 5개 역할의 제한 권한도 확인했다. 컨테이너와 전체 브라우저 검증은 해당 PR의 CI 결과를 기준으로 한다.
