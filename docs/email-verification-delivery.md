# 이메일 확인과 복구 안내 발송

2026-11-26 기준 서버 연결 모드의 구현입니다. 이메일 주소 확인, 비밀번호 복구, 암호화된 발송 대기열과 별도 발송 작업자를 제공합니다. AWS SES 어댑터는 구현했지만 실제 발송 계정·도메인·권한을 만들거나 고객에게 메일을 보내지는 않았습니다. 테스트는 로컬 비공개 메일함과 주입한 SES 클라이언트로 수행합니다.

## 이메일 확인과 거래 자격

신규·기존 회원 모두 `users.email_verified_at=NULL`로 시작합니다. 과거 로그인이나 테스트 고객 승인 이력으로 이메일 소유를 추정하지 않습니다. `MemberProfile.emailVerifiedAt`과 `GET /api/auth/email`에서 확인 상태를 반환합니다.

이메일 확인 요청과 완료에는 로그인 쿠키와 `X-Aqua-Account` 일치가 필요합니다. 확인 처리 트랜잭션 안에서도 세션을 다시 검사합니다. 확인 코드는 해당 회원과 가입 이메일에 묶이며, 다른 회원의 로그인이나 비밀번호 복구 코드로 대신할 수 없습니다. GET 요청은 이메일을 확인하지 않습니다.

코드는 32바이트 난수의 64자리 16진수 문자열입니다. 사용자는 이메일의 코드를 복사해 확인 화면에 붙여 넣습니다. 화면은 코드를 메모리에만 두고 URL·localStorage·로그에 저장하지 않습니다. 서버에는 인증용 해시만 저장하며, 발송에 필요한 원문은 별도로 암호화합니다. 코드는 15분간 유효하고 재발급하면 이전 코드는 무효가 됩니다.

동일 회원이 이미 사용한 같은 확인 코드를 다시 보내면 기존 확인 결과를 반환합니다. 소비된 확인 기록은 재시도를 위해 유지하며, 비밀번호 재설정 시 제거합니다. 이미 확인된 회원이라도 임의의 코드가 유효해지는 것은 아닙니다. 확인되지 않은 만료 코드는 한 번에 최대 256개씩 전용 정리 함수로 제거합니다.

| 동작 | 조건 |
| --- | --- |
| 회원 간 새 송금 | 보내는 회원과 받는 회원 모두 고객 상태 `active`이고 이메일 확인 완료 |
| 새 카드 승인 | 고객 상태·이메일 확인·기존 카드 상태 및 한도 정책 충족 |
| 카드 잠금 해제 | 고객 상태 `active`이고 이메일 확인 완료 |
| 카드 잠금·기존 결제 매입·취소·환불 | 기존 처리 정책 유지 |
| 완료된 요청 재조회 | 현재 이메일 상태와 무관하게 원래 결과 유지 |

이메일 확인은 고객 심사를 승인하거나 동결을 해제하지 않습니다. 반대로 테스트 운영자가 고객 상태를 `active`로 바꿔도 이메일 확인을 대신하지 않습니다. 새 카드 정책 버전 3은 결정 당시 이메일 확인 시점을 기록하며 기존 승인·거절·운영 보고서는 변경하지 않습니다.

이메일 주소와 확인 시점은 현재 변경 API가 없습니다. DB도 주소 변경, 확인 시점 교체·취소, 가입 시 확인 값 주입을 막습니다. 향후 이메일 변경은 별도 재확인·복구·거래 제한 절차와 마이그레이션이 필요합니다.

## 비밀번호 복구

기존 복구용 토큰은 이메일 확인 토큰과 다른 테이블·경로에서 처리합니다. 복구 요청은 계정 존재 여부와 무관하게 일반적인 안내 응답을 반환합니다. 토큰 교체와 발송 큐 저장을 한 트랜잭션에서 처리하므로 큐 저장에 실패하면 이전 토큰이 유지됩니다. 이 실패도 특정 주소의 가입 여부를 드러내지 않도록 일반 응답으로 처리하고, 개인정보가 없는 `auth_mail_enqueue_failed` 이벤트만 기록합니다.

발송 대기열 설정이 없으면 새 안내 요청은 503을 반환합니다. 이미 발급된 유효한 코드를 확인하고 비밀번호를 변경하는 경로는 발송 설정에 의존하지 않습니다. 비밀번호 재설정은 모든 기존 세션과 대기 중인 이메일 확인 코드를 폐기합니다. 이미 확인한 이메일의 소유 확인 기록은 유지합니다.

이메일 확인 요청은 회원당 15분에 3회, IP당 15분에 10회로 제한합니다. 코드 확인은 회원당 15분에 5회, IP당 15분에 10회로 제한합니다. 이 제한은 PostgreSQL을 공유하는 서버·세션 사이에도 적용됩니다.

## 발송 대기열과 권한

`auth_mail_outbox`에는 AES-256-GCM으로 암호화한 수신 주소·코드·목적·유효기간을 저장합니다. 암호문은 메시지 ID, 목적, DB 스키마와 형식 버전에 연결됩니다. 인증·복구 토큰과 큐 행은 같은 트랜잭션에서 저장합니다. 외부 전송은 커밋 이후 별도 작업자가 수행합니다.

API에는 큐에 추가하는 함수만, 발송 작업자에는 작업 획득·결과 기록·통계 함수만 허용합니다. 작업자는 회원·세션·토큰·원장·큐 테이블을 직접 조회하거나 수정할 수 없습니다. 암호화 키가 있는 신뢰된 API는 코드를 발급하는 주체이며, 이 권한 분리가 API 전체 침해를 막는다는 의미는 아닙니다.

- 작업 임대는 최대 30초이며 외부 발송은 최대 10초로 제한합니다.
- 임대 토큰과 버전이 일치하는 작업자만 결과를 기록할 수 있습니다.
- 공급자 전송 시도는 최초 시도를 포함해 최대 총 5회입니다. 응답 유실 후에는 같은 메시지·코드가 중복 도착할 수 있습니다.
- 만료·사용·재발급된 코드는 다음 작업 획득 시 발송에서 제외합니다. 이미 전송 중인 메일은 회수할 수 없습니다. 도착해도 폐기된 코드로 인증할 수 없습니다.
- 작업자에 해당 암호화 키가 없으면 원문을 복호화하거나 메일을 보내지 않고 30초 뒤 다시 확인합니다. 이 대기는 공급자 발송 횟수에 포함하지 않으며 코드 만료까지로 제한됩니다.
- 인증에 실패한 암호문은 사용하지 않습니다. 완료·폐기·최종 실패한 작업의 암호문은 제거하고 처리 메타데이터·이력은 남깁니다.

`sent`는 SES가 요청을 받아들였다는 의미입니다. 수신함 도착, 열람, 반송 여부를 뜻하지 않습니다. 반송·불만 알림 수집과 중앙 알림 연결은 별도 운영 과제입니다. `auth_mail_health` 로그에 적체·실패·가장 오래된 대기 시각을 기록하므로 운영 환경에서는 이를 지표와 알림에 연결해야 합니다.

## 설정과 실행

API와 작업자에 같은 키링을 제공하고, 작업자는 별도 DB 역할을 사용합니다. `.env.example`의 로컬 연결 정보는 개발용입니다. 실제 키를 저장소나 실행 로그에 넣지 않습니다.

| 설정 | 용도 |
| --- | --- |
| `AQUA_AUTH_MAIL_KEYS` | `{키ID: 32바이트 키의 base64}` JSON, 최대 8개 |
| `AQUA_AUTH_MAIL_ACTIVE_KEY` | 새 암호문에 사용할 키 ID |
| `DATABASE_AUTH_MAIL_ROLE` | 마이그레이션 시 권한을 부여할 별도 역할 |
| `AUTH_MAIL_DATABASE_URL` | 작업자 전용 PostgreSQL 연결 |
| `AQUA_AUTH_MAIL_TRANSPORT` | `file` 또는 `ses`, 명시적 선택 필수 |
| `AQUA_MAIL_DIR` | 개발용 비공개 파일 메일함 |
| `AQUA_AUTH_MAIL_POLL_MS` | 250~60,000ms, 기본 1,000ms |
| `AWS_REGION`, `AQUA_AUTH_MAIL_FROM` | SES 리전과 검증된 발신 주소 |
| `AQUA_AUTH_MAIL_SES_CONFIGURATION_SET` | 선택적 SES 구성 세트 |

```bash
npm run db:migrate
npm run server:dev
# 별도 프로세스에서 실행
npm run server:mail:worker
# 작업 하나만 처리하려면
npm run server:mail:worker -- --once
```

`file` 전송기는 production에서 거부합니다. 개발 메일함은 0700 디렉터리, 0600 파일을 사용합니다. 실제 메일을 보내지 않으며 생성된 파일에는 인증 비밀값이 있으므로 웹 정적 경로나 공개 결과물에 포함하지 않습니다. 같은 메시지 재시도는 기존 파일 내용을 검사하며 덮어쓰지 않습니다.

운영 SES 작업자는 AWS SDK 기본 자격증명 체인과 작업 역할을 사용합니다. 발신 도메인·주소 검증, SES 발송 허용 범위와 한도, `ses:SendEmail` 최소 권한, DNS 인증, 반송·불만 처리를 준비해야 합니다. 실제 자격증명이나 유료 리소스는 이번 작업에서 생성하지 않았습니다. 잘못된 설정을 개발 메일함으로 대체하지 않습니다.

키 교체는 작업자 키링에 새 키를 먼저 추가하고, API의 활성 키를 바꾼 뒤, 이전 키로 생성된 미완료 메시지가 없어졌는지 확인하는 순서로 진행합니다. 이전 키를 쓰는 대기 작업과 백업 복구 요구를 확인하기 전 키를 제거하지 않습니다. 키는 운영 비밀값 관리 시스템에 별도로 보관합니다.

백업에서 대기 메일을 복구할 때는 원래 스키마 이름과 해당 키링을 함께 복원해야 합니다. 암호문이 스키마 이름에 연결되어 있으므로 이름을 바꿔 복원한 큐는 그대로 발송할 수 없습니다.

작업자 컨테이너는 HTTP 서버가 아닙니다. 기존 API 이미지의 HTTP healthcheck를 그대로 적용하지 말고 작업자용 프로세스·로그·적체 감시를 구성해야 합니다.

## 업그레이드와 검증

011·012는 기존 마이그레이션을 수정하지 않고 추가합니다. 구버전 API·작업자를 비운 뒤 DB 백업, 마이그레이션·권한 적용, 새 API·발송 작업자 시작 순으로 전환합니다. 기존 회원의 이메일도 기본 미확인이므로 새 거래가 제한됩니다. 기존 결제 보류액이나 금융 이력은 바꾸지 않습니다. 이미지 교체만으로 과거 DB 버전으로 되돌리지 않습니다.

`npm run test:email:browser`는 별도 스키마에서 제한된 API·발송 역할과 실제 로컬 파일 작업자를 실행합니다. 먼저 `npm run build:server`, `npm run build:connected`를 실행하고 로컬 `TEST_DATABASE_URL`, `DATABASE_URL`, `AUTH_MAIL_DATABASE_URL`을 설정합니다. 외부 SES에 메일을 보내지는 않습니다.

실제 본인확인 연동, MFA·패스키, 금융 거래의 추가 인증, 이메일 변경, 실서비스 메일 도달률 검증은 이 구현에 포함되지 않습니다.

## SES 반송·불만 처리 시험

격리된 샌드박스에서 반송이나 스팸 신고 뒤 발송 대기열의 동작을 시험할 수 있습니다. 마이그레이션 025와 전용 로그인 권한을 적용하고, 발송 작업자가 한 번 이상 가져간 테스트 메일의 UUID와 받는 주소를 준비합니다. 운영 명령에는 `AUTH_MAIL_FEEDBACK_DATABASE_URL`로 전용 로그인을 연결합니다. 마이그레이션 시 권한을 부여할 역할은 `DATABASE_AUTH_MAIL_FEEDBACK_ROLE`입니다.

아래 파일은 SES 구성 세트의 단일 수신자 이벤트 형식입니다. 예시의 주소와 `aqua-message` 값을 해당 테스트 메일에 맞게 바꿉니다. SNS 봉투가 있는 경우 내부 메시지가 이 형식입니다.

```json
{
  "eventType": "Bounce",
  "mail": {
    "destination": ["member@example.test"],
    "tags": { "aqua-message": ["00000000-0000-4000-8000-000000000000"] }
  },
  "bounce": {
    "bounceType": "Permanent",
    "feedbackId": "sample-feedback-1",
    "bouncedRecipients": [{ "emailAddress": "member@example.test" }]
  }
}
```

```bash
AQUA_AUTH_MAIL_FEEDBACK_MODE=sandbox npm run server:mail:feedback -- ./bounce.json
```

| 이벤트 | 이후 발송 |
| --- | --- |
| 영구 반송(Permanent), 스팸 신고(Complaint) | 해당 회원의 인증·복구 메일 발송 중단 |
| 일시 반송(Transient) | 이후 발송 허용 |
| 스팸 아님(not-spam) | 이력만 추가. 이전 중단 결정 유지 |

발송 대기 중이던 메일은 작업자가 가져갈 때 폐기합니다. 새 요청은 평소와 같은 사용자 응답을 돌려주고 인증 메일의 암호문을 저장하지 않습니다. 작업자가 이미 가져간 메일은 발송을 마칠 수 있습니다. 같은 이벤트 ID로 다시 실행하면 첫 수신 결과를 반환하고, 내용이 달라지면 충돌로 처리합니다. 감사 이력에는 이벤트 ID, 메일·회원 식별자, 분류, 시각과 처리 역할을 기록합니다.

이 명령은 기본적으로 비활성화되며 `NODE_ENV=production`에서도 차단됩니다. 실제 서비스 도입에는 SES 구성 세트의 이벤트 전달 대상, 수신 경로의 AWS 계정·리전 및 권한 검증, 재처리 큐와 전달 지연 감시를 별도로 연결하고 실제 반송·불만 수신을 확인해야 합니다.
