# 카드 잠금과 새 결제 승인

`007_card_authorization_policy.sql`은 Aqua sandbox 카드 상태를 테스트 원장의 새 승인 검사에 연결한다. 잠금 요청이 DB에 접수되면 발급사 확인을 기다리는 동안에도 새 승인을 중단한다. 이미 승인한 금액의 매입·취소·환불은 계속 처리한다.

현재 `authorize`는 내부 테스트 명령이다. 실제 발급사의 승인 요청이나 승인 완료 통보를 처리하는 계약은 아니다. 승인 완료 통보를 나중에 수신했을 때 현재 잠금 상태만 보고 정산 의무를 버리면 안 된다. 실시간 승인 응답 기한, 카드 매핑, 늦은 매입과 외부 대사는 파트너 계약에 맞춰 별도로 구현해야 한다.

## 승인 조건

현재 DB는 회원당 카드 한 장을 허용하고 카드의 회원·공급업체 식별자는 변경할 수 없다. 서버는 `userId`로 그 카드를 조회한다. 카드 ID를 생략해서 검사를 피하는 승인 경로는 없다. 여러 장을 지원하려면 공급업체 카드 식별자와 승인 입력 계약을 함께 변경해야 한다.

| 검사 결과 | 새 승인 |
| --- | --- |
| 연결된 카드 없음 | `CARD_NOT_ISSUED`로 거절 |
| 요청 상태 또는 확인 상태가 잠금 | `CARD_LOCKED`로 거절 |
| 양쪽 모두 사용 가능이지만 마지막 요청이 성공으로 확정되지 않음 | `CARD_STATUS_UNCONFIRMED`로 거절 |
| 양쪽 모두 사용 가능이고 요청 이력이 없거나 마지막 요청 성공 | 기존 잔액·리워드·페이백 검사를 수행 |

잠금 해제도 발급사가 성공을 확인해야 새 승인을 허용한다. 잠금 요청이 실패했더라도 마지막 잠금 의도를 지우지 않는다. 카드 설정 화면은 발급사가 확인한 상태와 새 결제 승인 가능 여부를 구분한다. 상태 조회가 오래됐거나 전송 결과를 모르면 승인 가능으로 단정하지 않는다.

## 결정 기록과 재전송

승인 성공과 위 세 가지 정책 거절을 `card_authorization_decisions`에 변경 불가 기록으로 남긴다. 정규화 입력, 카드 ID·버전·상태, 마지막 명령 상태, 정책 버전과 최초 결과를 보존한다. 정책 거절은 승인 보류액·원장 전표·리워드에 금액을 반영하지 않는다.

같은 `eventId`와 내용은 최초 결과를 돌려준다. 잠금 해제나 카드 등록 후에도 이전 정책 거절은 승인으로 바뀌지 않는다. 다른 내용이나 매입·환불에 그 이벤트 ID를 재사용하면 충돌이다. 별도의 결제 재시도에는 새 이벤트 ID를 쓴다. 기존 승인 성공도 잠금 후 재전송하면 최초 성공 응답을 그대로 반환한다.

DB 함수는 정책 거절을 `{ "declined": true, "code": "CARD_LOCKED" }` 같은 결과로 반환해 거절 기록을 커밋한다. `CardPaymentStore`는 커밋을 마친 뒤 이를 `LedgerError`로 전달한다. 트랜잭션 안에서 예외로 바꾸면 거절 기록까지 롤백되므로 이 순서를 유지한다. 잔액 부족·원장 오류 등 기존 금융 처리 실패는 직접 명령에서 트랜잭션을 롤백하며, inbox에서는 기존 확정 실패 정책을 따른다.

## 경합과 inbox

동일 이벤트 ID의 모든 종류는 공통 트랜잭션 잠금으로 직렬화한다. 새 승인은 회원, 발급사 카드, 금융 계정 순서로 잠그며 카드 잠금 변경과 승인이 같은 카드 행에서 순서를 정한다. 먼저 완료된 승인은 기존 승인으로 남고, 먼저 접수된 잠금 이후 새 승인은 거절된다. 승인 결과와 결정 이력은 함께 커밋한다.

inbox도 같은 함수를 사용한다. 정책 거절은 결정 이력과 `dead_letter`를 한 트랜잭션에 저장하며 자동·운영자 재처리를 허용하지 않는다. HTTP 202는 접수일 뿐이다. 카드 상태는 작업자가 실제 승인 명령을 처리할 때 검사한다. `event_received_at`은 최초 접수 시각이고 `decided_at`은 DB가 결정을 기록한 시각이다. 재전송으로 두 시각을 바꾸지 않는다.

API·수신·처리·발신 역할에는 결정 테이블의 직접 접근을 허용하지 않는다. 금융 처리 전용 내부 함수도 직접 실행할 수 없다. 새 승인 이벤트에는 대응하는 승인 결정이 있어야 한다는 지연 제약을 적용한다. 007 이전에 처리한 승인은 새 카드 연결 없이도 최초 응답 재전송과 후속 정산을 허용한다.

008 이후 [카드 거래 운영 조회](card-operations.md)로 승인 결정과 관련 원장·수신함 상태를 추적할 수 있다. 전용 운영 역할은 조회 기록을 커밋한 뒤 제한된 결과만 읽으며, 결제나 승인 결과를 바꿀 수 없다.

## 적용과 확인

기존 001~006 파일을 수정하지 않고 007을 추가한다. 배포 시 기존 승인 명령 실행기와 inbox 작업자를 중지하고 `npm run db:migrate`로 마이그레이션·역할 권한을 적용한 뒤, 거절 결과를 해석하는 새 서버 빌드로 재시작한다. API와 작업자는 시작 시 마이그레이션 일치를 검사한다. 카드가 자동 발급되지는 않는다.

작업자를 재시작하기 전에 대기 중인 승인 요청과 필요한 카드 연결을 확인한다. **007 이전에 접수됐지만 아직 처리하지 않은 승인도 새 정책을 적용받는다.** 카드가 연결되지 않은 상태로 처리하면 `CARD_NOT_ISSUED`로 최종 거절되며, 나중에 카드를 등록해도 같은 이벤트를 승인으로 바꿀 수 없다. 의도한 테스트 카드 매핑만 먼저 등록하거나 해당 거절 결과를 수용한 뒤 작업자를 재개한다. 이미 완료된 승인은 이 전환의 영향을 받지 않는다.

로컬 테스트 카드는 먼저 가입한 회원에 대해 등록한다.

```bash
npm run server:issuer -- register USER_ID sandbox-card-local active
```

같은 공급업체 카드 참조를 다른 회원에게 재사용하지 않는다. 잠금·해제와 발신 작업자는 [발급사 요청·복구](issuer-command-outbox.md)를 따른다. 실제 결제망에는 연결되지 않는다.

PostgreSQL 검사는 잠금과 승인 경합, 거절 재전송, 기존 매입·환불, inbox의 최종 거절, 변경 불가 이력, 권한 우회 차단과 구버전 업그레이드를 확인한다. 연결 브라우저 검사는 카드 설정 화면의 승인 가능 표시와 실제 서버 승인·거절을 함께 확인한다. 현재 변경의 검사 결과는 PR의 CI를 기준으로 한다.
