# 서울 스테이징 경보 수신·시점 복구 훈련

당직자는 점검이 끊겼을 때 받은 경보를 확인한다. 복구 담당자는 지정 시점까지의 거래가 남은 새 RDS 인스턴스에서 송금을 재개한다. 결과에는 각각의 시각과 증빙을 기록한다. 대상은 합성 잔액을 쓰는 서울 리전(`ap-northeast-2`)의 스테이징 PostgreSQL DB 인스턴스다.

처음 구축하는 계정은 원본 DB와 점검기를 먼저 준비한다. [서울 스테이징 설치](staging-setup.md)

## 로컬에서 먼저 검증할 범위

`npm run test:pitr`는 폐기할 PostgreSQL 18에 물리 기본 백업을 뜨고 거래를 더 만든 뒤 보관한 WAL을 지정 시각까지 재생한다. 시점 이후 거래가 원본에 실제로 반영됐는지, 복원본에 시점 이전 거래만 남았는지, 복원 후 같은 거래를 다시 보내도 금액이 맞는지 검사한다. 시험 거래의 정산 계정에는 목표 시각에 50 TEST_KRW가 있고 나중에 10을 환불한 원본에는 40이 남는다. 복원본에서 50을 확인하고 새로 5를 환불하면 45가 남아야 한다. 출력 시간은 새 복원 컨테이너 기동 요청부터 쓰기 가능한 DB가 될 때까지와 이후 새 카드 거래 검증까지의 경과 시간이다. AWS 할당·트래픽 전환·경보 수신 시간은 스테이징에서 따로 잰다. [로컬 시점 복구 훈련](../scripts/pitr-drill.sh) · [논리 백업 복원 훈련](server-development.md#postgresql-백업-복원-훈련)

## 복원할 시각 만들기

1. 이번 훈련만 쓸 스테이징 합성 회원 두 명을 정하고 거래 자격, 원금, 송금 한도를 확인한다. 두 계정의 시작 잔액과 서버의 릴리스 커밋을 기록한다. 예를 들어 보내는 회원의 원금이 10,000원, 받는 회원이 0원일 때 아래 금액을 그대로 쓸 수 있다.
2. 첫 송금 A로 1,000원을 보낸다. 스테이징의 정상 송금 흐름에서 성공 전표와 양쪽 잔액 9,000원·1,000원을 확인한다. 요청 전과 성공 후 원본 DB에서 각각 `SELECT clock_timestamp() AT TIME ZONE 'UTC'`를 조회해 UTC로 보관한다. 재전송할 때 필요한 요청 키는 훈련용 비공개 기록에 둔다. [송금 API와 재전송](server-development.md#두-계정으로-송금-확인)
3. A가 완료된 뒤 원본 DB 시계가 다음 초를 넘으면 해당 시각을 초 단위 UTC로 기록한다. 이 값이 `T`다. DB 시계가 `T`의 다음 초를 지난 뒤 서로 다른 요청 키로 두 번째 송금 B 2,000원을 보낸다. 원본에서 이번 전표와 잔액 7,000원·3,000원을 확인한다. 훈련 중 두 계정에서는 다른 거래를 하지 않는다.
4. RDS 자동 백업의 복구 가능 범위를 확인한다. 시작 시각은 `T`와 같거나 이전이어야 하고, 가장 최근 복구 가능 시각은 `T`를 지나야 한다. `T`는 A 커밋 뒤, B 시작 앞의 시각이어야 한다. 백업 보관 기간이 만료됐거나 두 거래 사이에 복구 시점을 특정할 수 없다면 새 합성 거래로 경계를 다시 만든다.

## AWS 읽기 전용 검사

AWS CLI v2가 스테이징 역할을 사용하고 있는 터미널에서 실행한다. `AQUA_DRILL_ACCOUNT`는 기대하는 AWS 계정 번호, `AQUA_DRILL_ENV`는 점검기의 CloudWatch 환경 이름이다. 스택명, 원본 DB 식별자와 SNS 주제 ARN은 해당 환경 배포 기록에서 가져온다. `AQUA_DRILL_UTC`에는 위에서 고른 `T`를 `YYYY-MM-DDTHH:MM:SSZ` 형식으로 넣는다.

```bash
python3 scripts/staging-preflight.py \
  --account "$AQUA_DRILL_ACCOUNT" --stack "$AQUA_DRILL_STACK" \
  --environment "$AQUA_DRILL_ENV" --db-instance "$AQUA_DRILL_SOURCE" \
  --topic-arn "$AQUA_DRILL_TOPIC" --restore-time "$AQUA_DRILL_UTC"
```

종료값 0이면 복구 가능 범위와 점검 시점의 지표·경보 설정을 확인한 것이다. 1이면 확인된 차단 항목을 조치한다. 2이면 입력, 읽기 권한 또는 조회 실패를 확인한다. 담당자는 출력과 별도로 스테이징 점검기의 DB 연결 대상이 이번 원본과 일치하는지 기존 배포 기록에서 대조한다. 읽기 역할에는 STS의 호출자 확인, RDS 인스턴스·자동 백업 조회, CloudFormation 스택·리소스 조회, Scheduler 스케줄 조회, CloudWatch 경보·지표 및 알림 음소거 규칙 조회(`cloudwatch:ListAlarmMuteRules`), SNS 주제 속성 조회 권한이 필요하다. [사전 검사](../scripts/staging-preflight.py) · [경보 구성과 경로](operations-monitoring.md)

## 당직자 수신 확인

1. 스테이징 시험 알림을 받을 당직자와 재개 담당자가 함께 시작한다. CloudFormation 출력 `MonitorScheduleArn`과 논리 리소스 `MissingMonitorAlarm`의 실제 이름을 확인한다. 스케줄이 켜져 있고 해당 경보가 `OK`인지 확인한다. 원래 스케줄 대상·주기·네트워크·실행 역할을 대조할 수 있도록 기록하고, 일정 재개 시각을 정한다.
2. Scheduler 콘솔에서 해당 스케줄의 상태만 일시 중지한다. 마지막 정상 표본 시각, 중지 시각, CloudWatch의 `ALARM` 전환 시각, 당직자가 해당 SNS 통지를 받은 시각을 UTC로 기록한다. 기본 경보는 5분 구간 3개가 누락되면 평가하며, 실제 통지에는 평가 지연이 더해질 수 있다.
3. `ALARM` 전환이 확인되거나 정해 둔 재개 시각이 오면 즉시 같은 스케줄을 켠다. 예를 들어 30분으로 예약했다면, 그때까지 경보가 오지 않아도 재개 담당자가 원래 설정으로 복원한다. 조기 중단할 때도 바로 켠다. 다음 정상 점검 표본과 `OK` 전환, 당직자의 복구 통지 수신까지 확인한다. 지정 시간까지 경보가 전환되지 않으면 감지 미확인으로 기록한다. CloudWatch 이력만 있고 당직자가 받은 메시지가 없으면 수신 미확인으로 남긴다.
4. 재개 후 읽기 전용 검사를 다시 실행한다. 감시가 회복된 뒤 RDS 복구를 시작하면 두 훈련의 장애 시각이 겹치지 않는다.

## RDS 시점 복구와 거래 재개

1. 읽기 전용 검사 결과의 `sourceDbiResourceId`가 **원본 스테이징 인스턴스**의 리소스 ID와 일치하는지 확인한다. 서울 리전 CloudFormation에서 [복구 템플릿](../infra/staging-pitr.yaml)으로 이번 훈련용 **새 스택**의 변경 세트를 만든다. `SourceDbiResourceId`에는 원본 리소스 ID, `RestoreTime`에는 위의 `T`, `DBInstanceClass`에는 원본 엔진 버전에서 지원되는 크기를 넣는다. `VpcId`, `PrivateDBSubnetGroupName`, `VerifierSecurityGroupId`는 격리한 VPC·사설 DB 서브넷 그룹·검증 전용 보안 그룹을 지정한다. 지정한 서브넷과 보안 그룹이 같은 VPC에 있고 검증 앱에서만 TCP 5432로 접근할 수 있는지 확인한다. [Amazon RDS 시점 복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)
2. 변경 세트에는 공개 접근이 꺼진 새 인스턴스와 전용 보안 그룹이 생성된다. 원본을 변경하는 항목이 없어야 한다. 복원된 발송 대기열에는 과거 요청이 남을 수 있다. 복원본에 작업자를 연결하지 않고 훈련용 앱의 발급사·메일 발송 권한과 네트워크 접근을 제한한다. 기존 서비스의 DB 비밀, DNS, 스케줄은 유지한다. 훈련 장애 선언 시각을 `T0`로 기록하고 변경 세트를 실행한다. 별도 RDS 비용이 발생한다. 내부 훈련 기록에는 요청 시각과 스택 이벤트를 남긴다.
3. 스택의 `RestoredDBIdentifier`로 RDS 복원본을 조회한다. `available` 시각, 새 엔드포인트, 원본과의 리소스 ID 차이, 저장소 암호화와 키, 포트, 보안 그룹 및 파라미터 그룹을 확인한다. 새 엔드포인트의 호스트 이름과 신뢰한 RDS CA로 TLS 연결을 검증한다. 훈련용 API와 검사기만 새 엔드포인트에 연결한다. 같은 릴리스에서 마이그레이션 체크섬과 실행 역할을 확인하고, `/api/health`와 복원본 전용 점검이 성공하는지 확인한다. 점검 로그는 별도의 환경 이름과 로그 그룹으로 보내서 스테이징의 기존 경보와 섞이지 않게 한다.
4. 두 회원의 전표와 잔액을 읽는다. A 한 건, B 없음, 잔액 9,000원·1,000원이어야 한다. 합성 계정으로 A를 원래 키·금액·수취인 그대로 재전송해 A의 전표와 잔액이 유지되는지 본다. 새 요청 키로 1,000원을 보내서 8,000원·2,000원이 되는지 확인한다. 내부 원장 대사 차이 0건, `/api/health` 정상, 새 거래 성공 전표를 확인한 시각을 `T1`로 기록한다. 원본에서는 계속 A와 B가 모두 보이는지도 확인한다.
5. 원본의 라우팅·작업자·모니터링 상태를 확인한다. 복구 템플릿의 임시 DB에는 자동 백업 보존이 꺼져 있고 스택 삭제 시 최종 스냅샷이 생성되지 않는다. 필요한 증빙을 먼저 보관한다. 훈련용 앱의 접속을 닫고 스택과 복원본 식별자를 다시 대조한 뒤 **이번 훈련 스택**을 삭제한다. 리소스 삭제 완료까지 확인한다.

## 결과에 남길 값

| 항목 | 기록 방법 |
| --- | --- |
| 경보와 수신 | 마지막 정상 표본, 중지, `ALARM` 전환·실제 수신, 재개, 첫 정상 표본, `OK` 전환·실제 수신 시각. 상태 이력과 두 통지의 비공개 증빙 참조를 함께 남긴다. |
| 거래 복구 시간 | `T1 − T0`와 세부 시각(복원 요청, RDS 사용 가능, 훈련용 서비스 정상, 거래 성공)을 기록한다. 고객용 도메인 전환을 생략했다면 결과에 명시한다. |
| 데이터 복구 범위 | 목표 `T`, 자동 백업의 시작·끝 시각, A와 B의 원본·복원본 존재 여부와 합성 잔액을 기록한다. `T0 − T`는 선택한 복구 시점의 나이다. 오래된 시각을 의도적으로 골랐다면 그 차이로 운영 RPO 충족을 판정할 수 없다. 장애 시점에 가장 최근 사용 가능한 복구 지점과 마지막 복구된 거래를 측정한 뒤 합의한 목표와 대조한다. |
| 인수 판단 | 실행 커밋, 환경, UTC 시각, 담당 역할, 실패·미확인 항목과 재검사 결과를 기록한다. 공개 PR에는 집계값과 익명화한 결과만 남긴다. 계정·리소스 식별자, 구독자의 실제 주소, 인증 정보와 원본 전표는 공개 기록에서 제외한다. |
