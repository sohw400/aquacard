# 발급사 명세서와 카드 정산 원장 대사

정산 담당자가 하루치 매입·환불 명세서를 가져오면 Aqua의 카드 정산 계정에 반영된 거래와 한 건씩 대조한다. 현재 형식은 공급사와 무관한 샌드박스 계약이며 통화는 `TEST_KRW`다. Reap 원본의 실제 열, 통화, 마감 시각과 거래 식별자 매핑은 제휴 테스트 자료로 확인해야 한다.

## 명세서 준비

UTF-8 JSON 일반 파일 하나에 한 영업일의 매입과 환불을 담는다. 파일은 최대 4 MiB(4,194,304바이트), 행은 최대 10,000개다. 명령에는 실제 파일 경로를 전달한다. [합성 명세서 예제](examples/issuer-statement.json)

| 항목 | 작성 기준 |
| --- | --- |
| `version`, `currency` | 숫자 `1`, 문자열 `TEST_KRW`를 쓴다. |
| `businessDate` | `YYYY-MM-DD` 형식의 한국 날짜다. `2025-11-26`을 지정하면 원장에 기록된 시각이 UTC 11월 25일 15시 이상, 26일 15시 미만인 정산 분개를 읽는다. 한국에서 해당 영업일이 끝난 뒤에 실행한다. 당일이나 미래 영업일을 요청하면 종료값 2를 반환한다. |
| `controls` | `rowCount`는 전체 행 수, `capturedWon`과 `refundedWon`은 각각 매입 총액과 환불 총액이다. 행에서 다시 계산한 수치가 이 값들과 일치해야 한다. 빈 날은 행 수 0, 두 총액 `"0"`, 빈 배열을 명시한다. |
| `rows` | 한 행은 `eventId`, `paymentId`, `kind`, `amountWon`으로 구성한다. `kind`는 매입 `capture` 또는 환불 `refund`다. 원 단위 금액은 둘 다 양의 정수를 십진 문자열로 쓴다. 예를 들어 30원 환불은 `"30"`이다. |
| 식별자 | `eventId`는 개별 매입 또는 환불의 고유 참조, `paymentId`는 같은 결제를 묶는 참조다. 한 결제에 부분 환불이 두 번 있으면 결제 번호는 같고 이벤트 번호는 두 개다. 양쪽 시스템의 참조가 다르면 변환 단계에서 검증한 대응표가 필요하다. |

거래 원본의 참조는 영문자나 숫자로 시작하는 1~128자이며 구분 기호는 `.`, `_`, `:`, `-`를 쓸 수 있다. 일반 참조는 그대로 사용한다. 13자리 밀리초 시각처럼 연속 13~19자리 숫자나 카드번호와 비슷한 구분 표기가 포함된 거래 참조는 아래 절차로 별칭을 만든다. 기존 원장에 기록된 동일 참조도 읽을 때 같은 별칭으로 표시된다.

명세서가 제공하는 총액과 건수는 별도로 보관해 변환 결과를 검산한다. 행과 검산값을 같은 불완전한 파일에서 함께 만들면 누락된 원본 페이지를 발견할 수 없다. 공급사 재전송으로 같은 이벤트가 여러 줄에 들어왔다면 줄을 모두 보존해 중복을 점검한다. 카드번호·성명·가맹점명·이메일 또는 발급사 원문은 정규화 파일에 넣지 않는다.

영업일은 Aqua 원장 반영 시각을 기준으로 정한다. 발급사가 다음 날 매입을 청구하거나 자체 마감 시각을 쓰면 같은 거래가 서로 다른 날짜에 보일 수 있다. 양쪽 반영 시각, 원본 파일의 배치 및 마감 시각을 확인해 시차를 기록한다. 승인 보류, 미사용 승인 해제, 수수료, 환차, 차지백은 현재 명세서의 매입·환불 범위 밖이다. USD·KRW 원본을 받으면 먼저 계약 통화·환율·수수료와 정산일 매핑을 정해야 한다.

## 숫자가 긴 거래 참조 처리

마이그레이션 019는 원장 스키마마다 32바이트 키 하나를 만든다. 이 키는 금융 원장과 함께 백업·복원한다. 원본 식별자나 기존 분개는 수정하지 않는다. 발급사 자료를 준비하는 담당자는 원본에서 필요한 열만 뽑아 위 명세서 형식 또는 은행 대사용 정산 통지서 형식으로 정리한다. 원본 카드번호나 예금주 정보를 거래 참조로 쓰지 않는다.

DB 소유자는 보호된 서비스 연결로 해당 스키마의 `settlement_reference_key`에서 `encode(signing_key,'hex')`를 한 번 읽어 권한 있는 정규화 작업에 비밀 파일로 배포한다. 정상 스키마에는 `singleton = true`인 행 한 개가 있다. 채팅·명령 인수·로그를 거치지 않고 비밀 저장소 또는 소유자만 읽는 파일로 전달한다. 입력 키 파일은 16진 문자 64개이며 마지막 줄바꿈은 선택 사항이다. 작업자는 키 파일을 0400 또는 0600으로 마운트하고 `SETTLEMENT_REFERENCE_KEY_FILE`에 그 경로를 설정한다. 이 파일 준비 명령에는 DB 접속 권한이 필요 없다. 일상적인 대사 계정에는 키를 제공하지 않는다.

```bash
umask 077
npm run --silent server:normalize:references -- issuer issuer-source.json > issuer-normalized.json
npm run --silent server:normalize:references -- advice advice-source.json > advice-normalized.json
```

두 명령의 종료값 0을 확인한 뒤 결과 파일을 대사 명령에 전달한다. 원본과 결과는 별도의 경로를 쓴다. 금액·건수·중복 이벤트는 보존한다. 입력과 오류에는 동일한 형식·용량 검사를 적용한다. 배포 이미지에서는 `node dist-server/normalize-settlement-refs.js issuer|advice FILE`을 쓴다. 이미 사용하던 일반 참조 명세서는 그대로 대사할 수 있고, 보고서의 파일 해시는 대사에 실제 전달한 바이트에 해당한다.

다른 정규화 구현에서는 `HMAC-SHA-256`의 키로 위 32바이트, 메시지로 UTF-8 문자열 `AquaCard/settlement-reference/v1/event:<원본>` 또는 `AquaCard/settlement-reference/v1/payment:<원본>`을 사용한다. 다이제스트 전체를 소문자 16진수 64자로 표현하고, 각각 `~e1.` 또는 `~p1.`을 붙인다. 참조의 대소문자와 구분기호를 보존한다. 정산 통지서의 `eventIds`는 명세서의 이벤트와 같은 규칙을 따른다. 원본 참조에는 `~`가 허용되지 않아 원본 변환 단계에서 별칭 사칭을 거절한다. 정규화가 끝난 파일은 대사 명령으로 직접 읽는다. 은행의 배치·기장 참조와 계좌 별칭은 기존 규칙을 유지한다.

스키마 키를 덮어쓰면 이전 결과와 연결할 수 없다. 키 손실 시 해당 원장의 백업과 비밀 보관본으로 복구한다. 교체가 필요하면 새 별칭 버전, 과거 버전 조회와 증빙 연결을 함께 배포한다.

## 실행

DB 관리자는 전용 로그인 역할을 준비하고 그 이름을 `DATABASE_SETTLEMENT_ROLE`에 지정한 상태로 `npm run db:migrate`를 실행한다. 로컬 개발용 역할 이름은 `aqua_settlement`다. 실행 환경의 `SETTLEMENT_DATABASE_URL`에는 이 계정의 연결 정보를 넣고 `DATABASE_SCHEMA`를 확인한다. 운영 연결에는 신뢰한 `DATABASE_CA_FILE`과 DB의 호스트 이름을 사용한다. 로컬 개발 환경에서는 저장소 루트에서 예제 파일을 직접 지정할 수 있다.

```bash
npm run --silent server:reconcile:statement -- docs/examples/issuer-statement.json
```

배포 이미지와 같은 빌드로 실행하려면 연결 정보를 환경에 제공한 뒤 다음 명령을 쓴다.

```bash
npm run build:server
node dist-server/reconcile-issuer-statement.js docs/examples/issuer-statement.json
```

예제 파일은 PostgreSQL 복원 훈련의 마지막 거래까지 반영한 DB에 대응한다. 한 결제에서 100원을 매입하고 30원을 환불했고, 다른 결제에서 50원을 매입했다. 리워드와 원금을 함께 쓴 매입도 명세서에서는 한 건이다. 해당 DB에서 대사하면 두 결제의 이벤트 3개가 일치하고 매입 총액은 150원, 환불 총액은 30원, 순액은 120원이다. [복원 훈련 데이터](../scripts/recovery-fixture.ts)

## 결과 확인

| 종료값 | 의미와 할 일 |
| --- | --- |
| `0` | 해당 날짜의 이벤트가 모두 일치한다. 표준 출력에 JSON 보고서가 나온다. `matchedEventCount`와 `statementTotals`, `ledgerTotals`의 건수·매입·환불·순액을 기록한다. |
| `1` | 검사한 자료에서 차이를 발견했다. `findingCount`는 차이가 있는 이벤트 번호의 수다. `findings`에서 해당 번호와 양쪽 내역을 확인한다. 기본 상세 출력은 100개까지다. `findingsTruncated`가 참이면 전체 차이 수가 표시된 상세 목록보다 많다. |
| `2` | 대사를 완료하지 못했다. 표준 오류로 반환한 오류 코드와 함께 파일 형식·검산값·크기, DB 연결·역할·마이그레이션, 처리 가능한 행 수를 확인하고 같은 입력으로 다시 실행한다. |

`MISSING_IN_LEDGER`는 명세서에만 있는 거래, `MISSING_IN_STATEMENT`는 원장에만 있는 거래다. 파일 버전, 영업일 경계와 옆 날짜의 명세서, 미처리 카드 이벤트를 확인한다. `DUPLICATE_STATEMENT_EVENT`나 `DUPLICATE_LEDGER_EVENT`가 나오면 해당 참조의 건수와 내용을 조사한다. 총액은 중복 행까지 반영하므로 일치 여부는 이벤트 단위로 판단한다. `PAYMENT_ID_MISMATCH`, `KIND_MISMATCH`, `AMOUNT_MISMATCH`는 참조 매핑, 매입·환불 구분, 총액 기준을 확인한다. 매입과 환불이 같은 액수만큼 어긋나면 순액은 일치할 수 있다.

파일 원본과 검산값, 정규화 파일, 실행한 릴리스와 보고서를 접근이 제한된 정산 기록에 함께 보관한다. 보고서의 `statementSha256`은 명령에 전달한 정규화 파일 바이트의 SHA-256 값이다. 발급사 원본은 별도 증빙으로 관리한다. 재실행은 그 시점의 원장을 다시 읽으므로 지연 거래 반영 후에는 결과가 달라질 수 있다. 원장 수정이나 자금 이동은 발생하지 않는다. 조사에는 기존 카드 이벤트 조회와 내부 대사를 사용할 수 있다. [카드 운영 조회](card-operations.md) · [내부 대사](card-payment-server.md#카드-정산-내부-대사)

수수료와 은행 입출금까지 확인할 때는 정산 통지서와 은행 명세서를 함께 입력한다. 은행 대사 명령은 위의 매입·환불 대사를 다시 실행한 뒤 정산 묶음별 예정액과 기장액을 비교한다. 현재 정규화 형식은 TEST_KRW 한 통화를 다룬다. [은행 대사 실행과 예제](bank-settlement-reconciliation.md)

차이를 조사자에게 배정하고 근거와 독립 승인을 기록하는 절차는 [정산 차이 조사와 승인](settlement-cases.md)을 따른다.
