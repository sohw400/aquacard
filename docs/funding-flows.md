# 입출금 흐름

작성일: 2026-10-13

## 화면 구성

| 경로 | 입력 | 확인 | 처리 결과 |
| --- | --- | --- | --- |
| 카드·자산에서 충전 | 코인, 네트워크, 입금 예정 수량 | 체험용 주소, 최소액, 원화 전환액과 수수료 | 입금 대기 → 네트워크 확인 → 원화 전환 → 완료 |
| 결제 잔액에서 출금 | 코인, 네트워크, 받는 지갑, 주소, 출금 총액 | 전환비, 네트워크 비용, 최종 수령량, 남을 잔액 | 출금 확인 → 전송 중 → 완료 |
| 보유 코인에서 출금 | 네트워크, 받는 지갑, 주소, 코인 수량 | 네트워크 비용과 수령량, 남을 코인 | 출금 확인 → 전송 중 → 완료 |
| 리저브 넣기·빼기 | 금액, 전액 또는 빠른 금액 선택 | 출발·도착 잔액의 변경, 수수료 0원 | 완료 영수증 |
| 보유 코인의 원화 전환 | 코인 수량, 전액 선택 | 30초 견적, 평가액, 전환비, 받을 원화 | 완료 영수증 |

주요 화면에 즉시 원화 잔액을 추가하는 버튼은 제공하지 않는다. 새 입금은 전환이 끝난 뒤 카드 사용 가능 금액에 포함한다. 보유 코인은 직접 전환하거나 출금하기 전까지 유지한다.

## 입금 주소와 출금 주소

입금 주소는 `aqua-preview:polygon:usdc` 형식의 체험용 식별자다. 실제 체인이 사용할 수 있는 주소, 거래 해시, QR로 위장하지 않는다. 주소 주변과 최종 확인에서 실제 송금이 불가능함을 안내한다. `입금 확인 체험`을 눌러 네트워크 확인 이후 단계를 살펴볼 수 있다.

출금은 코인과 지원 네트워크를 함께 선택한다. 주소는 형식을 검사할 뿐 소유자·네트워크·수취 가능 여부를 인증하지 않는다. 특히 EVM 주소 형식은 네트워크 사이에서 같으므로 사용자가 선택한 네트워크를 최종 확인에 다시 보여준다. 예시 주소를 채워 개인 지갑 정보를 입력하지 않고도 체험할 수 있다. 실제 전송은 없다.

## 금액과 수수료

시세와 네트워크 비용은 제품 검토를 위한 고정 예시다. 운영 수수료·지원 네트워크는 파트너 계약 후 확정한다.

| 코인 | 네트워크 | 출금 네트워크 비용 예시 |
| --- | --- | ---: |
| USDC | Polygon | 140원 |
| USDC, USDT | Ethereum | 2,800원 |
| BTC | Bitcoin | 1,500원 |
| ETH | Ethereum | 2,000원 |

원화 전환비는 총평가액의 0.5%를 원 단위로 올림한다. 신규 입금에는 전환비, 결제 잔액 출금에는 전환비와 네트워크 비용을 적용한다. 보유 코인의 직접 출금에는 전환비가 없으며 네트워크 비용만 공제한다. 비용 공제 후 받을 금액이 양수여야 한다.

예를 들어 결제 잔액에서 USDC를 Polygon으로 10,000원 출금하면 전환비 50원과 네트워크 비용 140원을 차감한다. 받을 코인은 9,810원 상당이며 화면에는 코인 정밀도에 맞춘 수량을 표시한다. 리워드와 리저브는 출금 부족분에 자동 사용하지 않는다.

## 처리 중인 금액

출금 접수 시 총액 또는 코인 수량을 사용 가능 잔액에서 예약한다. 처리 중인 금액은 다른 출금·결제·리저브 이동에 사용할 수 없다. 예약 자산은 출금 완료 전까지 총 보유 자산에 포함한다. 자산 화면에서 처리 중인 금액과 입출금 현황을 따로 확인한다.

입금 대기와 출금 확인 단계에서는 취소할 수 있다. 전송 단계가 시작된 뒤에는 취소 버튼을 제공하지 않는다. 모의 출금 실패는 전송 전 단계에서 발생시키며 예약한 원금과 수수료 전액을 복원한다. 실패 후 다시 입력하면 새 견적과 별도 요청으로 접수한다.

작업과 단계별 예정 시각은 브라우저에 저장된다. 창을 닫거나 새로고침해도 자산의 입출금 현황 및 이용 내역에서 상세를 다시 열 수 있다. 같은 요청이나 완료 처리를 반복해도 잔액을 다시 변경하지 않는다. 기존 저장 데이터에 작업 목록이 없으면 빈 목록을 추가해 잔액과 카드 상태를 보존한다.

## 구현 경계

현재는 브라우저 안의 모의 상태 처리다. 단계 전환에 사용하는 약 3초 간격은 실제 체인의 처리 시간을 뜻하지 않는다. 출금 주소 인증, 서버 서명 견적, OTP·기기 인증, 수탁·거래 파트너, 실제 입금 감지·전송·정산, 여러 브라우저나 기기 사이의 동시성은 연동 전이다. 금융 서버 구조는 [백엔드 설계](funding-architecture.md)를 따른다.
